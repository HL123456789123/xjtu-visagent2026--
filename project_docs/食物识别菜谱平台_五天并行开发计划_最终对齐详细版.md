# 已有代码、创新与 V1 对齐原则

Adapter（适配层）是在已有实现和 V1 对外接口之间做字段、调用方式或异常转换的一小层代码。它的作用是保留能用的已有代码，同时只向前端或其他模块暴露 V1。

1. 已有代码不得直接推倒重写。先运行、列出当前输入输出，再判断能否保留内部实现。
2. 内部算法、组件拆分、缓存、日志和辅助字段可以保留或改进，只要不形成第二套公开接口。
3. 已有代码的对外接口与 V1 不一致时，优先增加 Adapter；确认无法适配后，才由原 owner 小范围修改。
4. 不得私自增加或修改对外 API 请求、响应、模型输出、Recipe JSON、SSE 事件和错误码；模块内部辅助字段允许增加。
5. 创新不得阻塞 Day3 Mock 全链路和 Day4 真实链路。先完成 P0，再做创新。
6. 创新必须可关闭、回滚或降级，并在 PR 中写清开关、影响和回滚方法。
7. V1 只在源码确实无法实现、出现严重安全问题或契约测试证明有明确错误时修改；必须经过提出冲突、闫灿宇确认、升级版本、吴雯更新 fixture/测试、相关成员统一修改的流程。

# V1.1 多图上传变更

1. Food multipart 公开字段统一为 `images`，每批 1～5 张 JPG/JPEG/PNG，单张不超过 10 MB，整批不超过 50 MB；一批只创建一个整数 `recognition_id`。
2. POST/GET 返回按上传顺序排列的 `images[{image_index,image_url}]`；每个模型候选携带 `image_index`，bbox 由此关联具体图片。
3. Food Service 按上传顺序循环调用单图 `FoodRecognitionProvider.recognize`，汇总时顺序拼接候选，不自动跨图去重；用户通过原 PUT 接口提交最终 `confirmed_ingredients`。
4. 批次采用原子失败：单图无检测结果是成功；任意文件或 Provider 处理失败时整批失败，不公开部分成功状态。
5. 刘楚涵负责多图选择、预览、删除、上传及错误提示；绕家辉负责 API、循环调用、汇总、Repository、JSON 存储和唯一 migration；黄小石的单图 Provider 不变；吴雯更新现有 Food canonical fixture 和契约测试。
6. Recipe 仍只读取最终 `confirmed_ingredients`，陈煜君和李晨宁负责的 Recipe、Chat、SSE 契约不变，不扩大其任务。
7. 旧单图实现通过 Adapter 迁移，公开 API 不长期兼容 `image` 字段，也不创建第二套接口文件或路径。

# 已经确定的实现

1. Food 接口同步识别每批 1～5 张 JPG/JPEG/PNG；单张最大 10 MB、整批最大 50 MB，默认阈值 0.25。
2. 黄小石在租用 GPU 服务器独立训练最稳定的 12 类，提交 `classes.yaml`；其他成员直接读取。
3. 用户确认食材后，后端使用固定 Prompt 让大模型直接生成结构化菜谱。
4. LLM JSON 先经 Pydantic 校验，再通过 Repository 保存。
5. 营养估算在同一 Recipe JSON 中，并显示固定免责声明。
6. 首次生成使用三个最小 LangGraph 节点；对话只分 `answer` 和 `update_recipe`。
7. SSE 只有 `token`、`recipe_updated`、`done`、`error`。
8. Day3 使用 Mock/Fake 跑全链路，Day4 换真实 YOLO/LLM，Day5 只回归和验收。

# 最小 LangGraph 流程

首次生成：

```text
START -> load_confirmed_ingredients -> generate_recipe -> validate_and_save -> END
```

对话：

```text
START -> load_recipe_context -> call_llm -> action
  answer -> END
  update_recipe -> 保存新版本 -> END
```

P0 不实现复杂路由、独立问答 Agent、独立营养 Agent、多 Agent 协作或自主工具编排。营养估算直接放在菜谱 JSON 中。

# 固定接口速记

| 项目 | V1 固定值 |
| --- | --- |
| Food API | `POST /api/food/recognitions` 的唯一文件字段为 `images`；另有 `GET /api/food/recognitions/{recognition_id}`、`PUT /api/food/recognitions/{recognition_id}/ingredients` |
| Recipe API | `POST /api/recipes`，`GET /api/recipes/{recipe_id}` |
| Chat API | `POST /api/chat/sessions`，`POST /api/chat/sessions/{session_id}/messages` |
| Food 前端 | `frontend/src/api/food.js` |
| Recipe 前端 | `frontend/src/api/recipe.js` |
| Chat 前端 | `frontend/src/api/chat.js` |
| 联调方式 | Day3、Day4 直接在 `develop` 联调，以集成记录和对应 Commit 哈希标记阶段状态 |
| SSE | `token`、`recipe_updated`、`done`、`error` |

模型固定接口：

```python
class FoodRecognitionProvider:
    def recognize(
        self,
        image_path: str,
        conf_threshold: float = 0.25,
    ) -> list[ModelDetection]:
        ...
```

| ModelDetection 字段 | 固定格式 |
| --- | --- |
| `class_name` | 英文类别名 |
| `confidence` | 0 到 1 |
| `bbox` | 对象，含 `x1`、`y1`、`x2`、`y2` |

无识别结果返回 `[]`；模型不可用抛出 `FoodModelUnavailableError`，Food API 转为 HTTP 503。`best.pt` 不进 Git。

模型 Provider 仍只处理单张图片；多图数量、大小、循环、`image_index`、结果顺序、批次失败和持久化全部由绕家辉负责的 Food Service/API/Repository 处理。
