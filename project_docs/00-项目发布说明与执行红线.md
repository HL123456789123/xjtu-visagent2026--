# 项目发布说明与执行红线

## 最终主流程

登录 → 上传 JPG/PNG → YOLO 返回候选食材 → 用户增删改并确认 → 大模型生成结构化菜谱 → 展示步骤和营养估算 → 对话回答或保存新版菜谱。

## 阅读顺序

1. 根目录 `AGENTS.md`：环境、包管理器、安装、启动、测试、构建、迁移、Docker 和 Agent 执行限制的唯一标准。
2. 本文件：先看主流程和红线。
3. `docs/contracts/api_v1.md`：实现前必须读本人相关章节；它是 API、字段、模型输出、Recipe JSON、SSE 和错误码的唯一标准。
4. `project_docs/食物识别菜谱平台_五天并行开发计划_最终对齐详细版.md`：看五天节奏。
5. `project_docs/任务分工速查表_最终对齐版.md`：确认角色、分支和交付物。
6. `project_docs/成员个人计划/姓名_五天个人任务计划.md`：执行本人每日任务。
7. `project_docs/02-已有代码与创新对齐说明.md` 和 `project_docs/03-已有代码对齐检查表.md`：已有代码先检查、再适配。

## 双唯一标准与环境执行规则

- 根目录 `AGENTS.md` 是全组唯一环境和命令标准；`docs/contracts/api_v1.md` 是全组唯一接口标准。
- 五天计划和个人计划只规定任务、Owner、文件边界、优先级和交付物，不建立第二套环境命令或公开接口。
- README、课程讲义、旧提示或个人笔记中的命令与 `AGENTS.md` 冲突时，以 `AGENTS.md` 为准。
- 每个 PR 必须按 `project_docs/integration/pr_environment_checklist.md` 写清实际工作目录、实际执行命令、真实结果、未运行项及原因；未运行的测试、构建、迁移或 Docker 检查不得写成通过。
- 环境问题必须交给计划登记的指定 Owner 统一处理，其他成员不得自行切换包管理器、删除或重建锁文件、另建第二套环境方案。
- Day3 和 Day4 直接在 `develop` 联调，用集成记录和对应 Commit 哈希标记阶段状态；不再创建额外 `integration/*` 分支。个人临时分支通过 PR 合入 `develop` 后及时删除，`master` 只用于最终稳定版本。

## 三区规则

🔴 **红色区域：必须对齐。** 对外 API、请求响应字段、模型 `ModelDetection`、Recipe JSON、SSE 四类事件、错误码、固定文件名和分支名必须符合 V1。发现冲突先登记，不得单人私改。

🟡 **黄色区域：已有代码优先 Adapter。** Adapter 是把已有内部实现转换成 V1 对外格式的一小层代码。已有代码先运行，不直接推倒重写；能适配就保留内部实现，也不长期维护两套公开接口。

🟢 **绿色区域：允许创新。** UI、日志、缓存、内部辅助字段、训练方法、测试组织和 Prompt 内部写法可以改进，但必须不改变红色区域、不阻塞 P0，并可关闭、回滚或降级。

## Git 提交红线

- 正式开发必须使用真实 Clone，从 `develop` 创建本人固定分支，通过 PR 合入；不得直接在 `master` 开发或强推。
- 原则上只改负责文件；共享文件先向 owner 提交接线需求或取得明确授权。
- 不传整仓 ZIP，不人工复制粘贴合并，不提交 `.env`、API Key、`best.pt` 或大型数据集。
- 新依赖写入依赖文件；新增环境变量同步写入 `.env.example`，只放占位符。

- **Day3：** 用 Mock Provider 和 Fake LLM 跑通上传、确认、生成、展示、对话修改、`recipe_updated` 和重新 GET。
