# VisAgent 答辩讲稿

> 本讲稿对应 8 页答辩材料。所有模型指标、运行结果和风险说明均来自本次本机验证与仓库中已冻结的模型说明；未收到的训练材料不补造。

## 1. 问题与用户流程

我们解决的是“看到食材以后，怎样快速变成一份可以继续修改的菜谱”这个问题。用户上传一张或多张食材图片，系统先给出候选食材；用户确认后，系统生成菜谱，并允许围绕这份菜谱继续对话。整个流程不是把识别结果直接当作事实，而是保留人工确认这一步，减少误识别直接进入菜谱的风险。

## 2. 系统架构

前端负责上传、确认、菜谱展示和对话；后端提供鉴权、业务接口和 SSE 流式响应；PostgreSQL 保存用户、识别批次、菜谱版本和会话；Redis 与 MinIO 分别承担运行支撑和图片对象存储。识别与生成分别通过 Provider 配置进入 YOLO 和 LLM，容器化后由 Docker Compose 一次拉起五个服务。

## 3. YOLO 模型、12 类边界与人工确认

当前部署的是 food-model-v1.0 的 YOLO11s，输入尺寸 640，默认置信度阈值是 0.25。它只覆盖糖、草莓、牛肉、鸡肉、奶酪、牛奶、番茄、黄油、玉米、香蕉、鸡蛋和胡萝卜 12 类。冻结测试集上的 mAP50-95 是 0.62859，但这不是“任何食物都能识别”的承诺。遮挡、反光、低清晰度、域外食物和未训练类别都可能漏检或误检，所以产品中必须由用户确认候选食材。

## 4. 多图识别与食材确认

接口接受 `images` 数组，服务端为每张图片保存 `image_index`，因此多图结果可以回到原图片。候选食材在前端可以增删改确认；只有确认后的食材才进入菜谱生成。本轮还补齐了损坏或伪装图片的处理：图片无法解码时直接返回 `422 / INVALID_IMAGE_CONTENT`，不会把坏文件送入 YOLO 推理，也不会以 500 形式暴露给用户。

## 5. 真实 LLM 菜谱与版本化对话

菜谱创建产生 version 1。对话采用 SSE，普通聊天会输出 `token → done`；涉及改菜谱的指令会输出 `token → recipe_updated → done`，并把菜谱更新为 version 2。容器验收中已实际验证 Real LLM 返回结构化菜谱、`is_mock=false`，以及一次修改对话把版本从 1 升到 2。营养内容保留免责声明，不作为医疗或营养处方。

## 6. 历史恢复、数据看板、权限隔离

历史页记录当前用户自己的识别、确认食材、菜谱版本和会话摘要；菜谱页可通过 recipe id 恢复，不依赖浏览器 localStorage。个人数据看板统计本人识别批次、候选/确认食材、菜谱、会话和近期趋势。普通用户不能访问管理路由或管理员 API，验收中管理员 API 对普通用户返回 403。管理员身份在 Profile 页显示为“管理员”，本轮已用随机临时账号复验，并在验证后删除。

## 7. Docker、测试与持久化证据

本机用 Docker Compose 构建了 backend 和 frontend，五个服务均健康：PostgreSQL、Redis、MinIO、backend、frontend。Alembic 单一 head 与 current 一致。后端检查为 Ruff 通过、179 个测试通过；前端为 122 个测试通过并完成生产构建。Mock/Fake 与 YOLO/Real LLM 两轮链路均走通；后端重启、前端重启、`docker compose down` 后不带 `-v` 再启动，Recipe version 2 仍能读取，说明数据库命名卷的数据仍在。

## 8. 局限、风险与后续计划

当前最重要的边界有两点：第一，模型只对 12 类和相近数据分布负责；第二，真实 LLM 依赖网络与第三方服务，需要展示超时和格式不合格时的可理解错误。黄小石的训练集概览、results.csv、类别分布、脱敏样例和官方六目标演示图尚未收到，因此训练页只展示真实运行状态和真实空状态。后续收到材料后接入真实训练指标；小红书发布作为答辩后的扩展，不在冻结前再新增风险。
